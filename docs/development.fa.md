# راه‌اندازی محلی Infinitycolor

[English](development.md) · [معرفی ریپو](../README.md)

## ابزارها و تنظیمات

برای شروع، Node.js **20.19 یا جدیدتر از سری 20.x**، Git، pnpm **10.28.2** و
داکر کامپوز رو نصب کنید. بک‌اند تا نسخهٔ 20 از Node رو پشتیبانی می‌کنه. توی
ویندوز از پاورشل و داکر دسکتاپ با WSL2 استفاده کنید. اگر توی WSL2 کار می‌کنید،
ریپو و وابستگی‌ها رو هم همون‌جا نگه دارید؛ با عوض کردن سیستم‌عامل، وابستگی‌ها
رو دوباره نصب کنید.

اگر Corepack نصب نیست:

```bash
npm install --global corepack
corepack pnpm --version
```

برای کلون کردن ریپو از دکمهٔ Clone توی GitLab استفاده کنید، یا اول توی
`glab` وارد حساب‌تون بشید. بعد توی فولدر اصلی ریپو این دستورها رو بزنید؛
هم توی بش کار می‌کنن، هم توی پاورشل:

```bash
glab repo clone bel4/infinity
cd infinity
corepack pnpm install --frozen-lockfile
corepack pnpm --filter @repo/auth-core build
node scripts/setup-dev-env.mjs
node scripts/setup-dev-env.mjs --check
docker compose --env-file apps/backend/.env -f compose.dev.yml up -d
docker compose --env-file apps/backend/.env -f compose.dev.yml ps
```

صبر کنید وضعیت PostgreSQL به healthy برسه. اسکریپت راه‌اندازی، `apps/backend/.env`
و فایل‌های `.env.local` برنامه‌های وب رو فقط وقتی می‌سازه که وجود نداشته باشن؛
فایل‌های قبلی رو تغییر نمی‌ده. کلیدهای محلی و رمزهای هماهنگ دیتابیس رو هم خودش
تولید می‌کنه. `--check` فقط وجود فایل‌ها رو چک می‌کنه. از لاک‌فایل فعلی pnpm
استفاده کنید و توی ورک‌اسپیس npm install نزنید. اطلاعات سرویس‌های جانبی
به‌صورت پیش‌فرض خالی می‌مونن.

[فایل داکر کامپوز](../compose.dev.yml) دیتابیس و ردیس محلی پروژه رو اجرا می‌کنه:
PostgreSQL روی **5432** و Redis روی **6379**، فقط روی loopback در دسترس هستن.
برای صف‌ها هم یک ردیس جدا روی پورت 6381 با تنظیم noeviction اجرا می‌شه.

قبل از اجرای برنامه‌ها، پکیج [`@repo/auth-core`](../packages/auth-core) رو بیلد
کنید. برنامه‌ها خروجی‌های `dist` و `dist-cjs` این پکیج رو می‌خونن و `dev`
این خروجی‌ها رو نمی‌سازه. هر وقت کد پکیج رو تغییر دادید، بیلدش رو دوباره بزنید.

## اجرا و اولین چک

توی ترمینال اول، از فولدر اصلی ریپو بک‌اند رو اجرا کنید:

```bash
corepack pnpm --filter @repo/backend dev
```

وقتی بک‌اند آماده شد، http://localhost:1337/admin رو باز کنید و حساب مدیر
محلی Strapi بسازید. بعد توی یک ترمینال دیگه، از فولدر اصلی ریپو فرانت‌اند رو
اجرا کنید:

```bash
corepack pnpm --filter @repo/frontend dev
```

http://localhost:1337/api/_health رو باز کنید؛ باید `checks.db="ok"` و
`checks.redis="ok"` ببینید. هر دو سرویس باید `ok` باشن. بعد
http://localhost:2888 رو باز کنید و مطمئن بشید سایت بالا اومده و خطای اتصال
به API ندارید. کامپایل اولین اجرا ممکنه کمی طول بکشه.

## Auth و برنامه‌های دیگر

برای دیدن فروشگاه، همین بک‌اند و فرانت‌اند کافیه. اگر می‌خواید ورود با رمز،
پنل مدیریت یا بخش اجتماعی رو بررسی کنید، اول ساختار Auth رو توی همون دیتابیس
محلی `infinity_local` آماده کنید:

```bash
node --env-file=apps/auth/.env.local apps/auth/scripts/apply-migration.mjs
```

آدرس تولیدشدهٔ `AUTH_MIGRATION_DATABASE_URL` با کاربر مالک دیتابیس وصل می‌شه؛
`AUTH_DATABASE_URL` از نقش جداگانهٔ `infinity_auth_app` استفاده می‌کنه. اسکریپت،
این نقش و ساختار Auth رو می‌سازه و مایگریشن‌های افزایشی رو اعمال می‌کنه. روش
تبدیل URL به مسیر فایل توی این اسکریپت ممکنه با مسیر درایو ویندوز مشکل داشته
باشه. اگر به این خطا خوردید، کل محیط رو توی WSL2 اجرا کنید و وابستگی‌ها رو هم
همون‌جا نصب کنید.

هر کدوم از دستورهای زیر رو توی یک ترمینال جدا، از فولدر اصلی ریپو بزنید:

```bash
corepack pnpm --filter @repo/auth dev
corepack pnpm --filter @repo/admin dev
corepack pnpm --filter @repo/social dev
```

| برنامه | نشانی |
| --- | --- |
| Auth | http://localhost:2889 |
| پنل مدیریت | http://localhost:2891 |
| بخش اجتماعی | http://localhost:2890 |

`AUTH_STRAPI_BRIDGE_SECRET` باید توی بک‌اند و Auth یکسان باشه. برای آدرس‌ها هم
همیشه از `localhost` تنظیم‌شده استفاده کنید. رمزها و نقش‌های کاری توی Strapi
نگهداری می‌شن؛ Auth هویت‌های متصل و سشن‌ها رو مدیریت می‌کنه. جزئیات توی
[معماری](auth/architecture.md) و [راهنمای عملیات](auth/operations.md) اومده.

## اولین تست و داده‌های محلی

با حساب مدیر Strapi می‌تونید Content Manager محلی رو ببینید؛ این حساب با
حساب مشتری یا مدیر فروشگاه فرق داره. [کد راه‌اندازی بک‌اند](../apps/backend/src/index.ts)
نقش‌های کاری و دسترسی عمومی خواندن رو آماده می‌کنه، ولی کاتالوگ کامل یا حساب
آزمایشی برای ورود نمی‌سازه.

تا وقتی دادهٔ نمونه رو دریافت نکردید، این موارد رو چک کنید:

1. پنل Strapi باز بشه و کالکشن‌های Product، Variation و Stock رو ببینید.
2. `http://localhost:1337/api/products` پاسخ JSON بده؛ خالی بودن کاتالوگ طبیعیه.
   اگر 403 گرفتید، خطاهای شروع برنامه و دسترسی‌ها رو چک کنید؛ همهٔ دسترسی‌ها
   رو عمومی نکنید.
3. فروشگاه بالا بیاد و تست زیر، موجودی قابل‌فروش بعد از کسر رزروها رو بررسی
   کنه؛ این تست به سرویس خارجی یا دیتابیس پرشده نیاز نداره.

```bash
corepack pnpm --filter @repo/backend test:unit --runInBand src/api/cart/services/lib/__tests__/stock-available.spec.ts
```

فعلاً اسکریپتی که برای ساخت دادهٔ دموی عمومی نگهداری بشه نداریم. `seed:e2e`
مخصوص تسته؛ کنترل دیتابیس مقصد و پاک‌سازی خودش رو داره و برای راه‌اندازی روزمره
نیست. `seed:admin` قدیمی هم توکن Master API می‌خواد و فرض می‌کنه شناسهٔ نقش
local-user برابر 2 هست؛ اجرای اون لزوماً حساب معتبر پنل مدیریت فعلی نمی‌سازه.
برای امتحان کردن راه‌های ورود، این دستورها رو روی دیتابیس کاری‌تون اجرا نکنید.

از مسئول ریپو **دادهٔ تست برای محیط محلی** بگیرید که این موارد رو داشته باشه:

- یک دسته، یک محصول `Active` با اسلاگ یکتا و تصویر، یک ورییشن متصل با SKU یکتا
  و قیمت، و رکورد موجودی متصل با `Count > 0` و `reservedCount = 0`. آدرس یا
  اسلاگ محصول رو هم بگیرید تا راحت پیداش کنید.
- تنظیمات و ارتباط‌های منوی محلی که برای نمایش محصول لازمه. دسترسی عمومی
  خواندن محصول و دسته باید با کد راه‌اندازی هماهنگ باشه.
- برای سبد و تسویه، یک مشتری، آدرس، استان/شهر و روش ارسال ساختگی محلی.
  تنظیمات تست پرداخت یا پیامک باید جداگانه مشخص بشن.

وقتی داده‌ها آماده شدن، محصول رو باز کنید، ورییشن رو انتخاب کنید و به سبد
اضافه کنید. قیمت و موجودی نمایش‌داده‌شده باید با دادهٔ تست یکی باشه.

اگر روی حساب‌ها یا پنل مدیریت کار می‌کنید، از مسئول ریپو یک مشتری ساختگی،
تأییدشده و فعال توی Users & Permissions استرپی و یک حساب جدا برای همکار با نقش
مناسب کارتون بگیرید. اطلاعات ورود با رمز و اتصال درست هویت‌ها از طریق Auth
محلی هم باید آماده باشه. قبل از تست ورود فروشگاه یا پنل مدیریت روی 2891، Auth
رو اجرا کنید. تست پیامک و درگاه پرداخت به تنظیمات مشخص سرویس توسعه نیاز داره؛
اسکریپت راه‌اندازی این تنظیمات رو آماده نمی‌کنه.

## کجا کد بزنید و چه تست‌هایی بگیرید

| کار | مسیر کد | بررسی‌ها |
| --- | --- | --- |
| فروشگاه و حساب کاربری | [کد فرانت‌اند](../apps/frontend/src) | لینت، تایپ‌چک، تست و بیلد فرانت‌اند و تست مسیر مرتبط توی مرورگر |
| موجودی، کاتالوگ و سفارش | [APIهای بک‌اند](../apps/backend/src/api) | تایپ‌چک، تست واحد و بیلد بک‌اند و API محلی |
| نقش‌ها و راه‌اندازی | [شروع بک‌اند](../apps/backend/src/index.ts) | بررسی‌های بک‌اند و کارهای مجاز و غیرمجاز با کاربران محلی |
| سرویس‌های محلی | [ابزار راه‌اندازی](../scripts/setup-dev-env.mjs)، [Compose](../compose.dev.yml) | وجود فایل تنظیمات، سلامت دیتابیس و ردیس و API |

```bash
corepack pnpm --filter @repo/frontend lint
corepack pnpm --filter @repo/frontend check-types
corepack pnpm --filter @repo/frontend test --runInBand
corepack pnpm --filter @repo/frontend build
corepack pnpm --filter @repo/backend check-types
corepack pnpm --filter @repo/backend test --runInBand
corepack pnpm --filter @repo/backend build
```

چک‌های پکیجی رو بزنید که تغییر دادید. دستورهای `lint`، `check-types`، `test`
و `build` توی فولدر اصلی، کل ورک‌اسپیس رو با Turbo بررسی می‌کنن. [تست واحد محدود](../apps/backend/src/api/cart/services/lib/__tests__/stock-available.spec.ts)
بالا رو می‌تونید قبل از آماده شدن کاتالوگ و حساب‌ها هم اجرا کنید. تست‌های
دیتابیس واقعی، مرورگر، ایمپورتر و سرویس‌های جانبی، داده و محیط مستقل خودشون
رو می‌خوان؛ این‌ها جزو مراحل اولین اجرا نیستن.

## توقف، اجرای دوباره و رفع خطا

هر برنامه رو با Ctrl+C ببندید. برای توقف کانتینرهای دیتابیس و ردیس، بدون
پاک شدن داده‌ها، این دستور رو بزنید:

```bash
docker compose --env-file apps/backend/.env -f compose.dev.yml down
```

برای اجرای دوباره، دستورهای `up -d` و `ps` بالا رو بزنید. وقتی سرویس‌ها سالم
بودن، برنامه‌ها رو توی ترمینال‌های خودشون اجرا کنید. بعد از تغییر تنظیمات هم
برنامه رو ری‌استارت کنید. برای رفع خطای معمولی از `down -v` استفاده نکنید.

- **به دیتابیس یا کش وصل نمی‌شه:** خروجی `ps` و دستور
  `docker compose --env-file apps/backend/.env -f compose.dev.yml logs --tail=80 postgres redis`
  رو ببینید. `DATABASE_PORT` و `REDIS_URL` بک‌اند رو با 5432 و 6379 چک کنید.
- **رمز دیتابیس رد می‌شه:** والیوم رمز اولیهٔ خودش رو نگه می‌داره و اسکریپت
  هم فایل‌های محلی قبلی رو تغییر نمی‌ده. این دو رو هماهنگ کنید؛ عوض کردن `.env`
  به‌تنهایی رمز داخل دیتابیس رو تغییر نمی‌ده.
- **فروشگاه به API اشتباه وصل می‌شه:** مقدار
  `NEXT_PUBLIC_API_BASE_URL=http://localhost:1337/api` و آدرس محلی متناظر توی
  `STRAPI_INTERNAL_URL` رو چک کنید. `.env.local` تنظیمات محلی فرانت‌اند رو مشخص
  می‌کنه. اگر دربارهٔ نبودن `main.env` قدیمی هشدار دیدید، لازم نیست فایل تنظیمات
  پروداکشن رو کپی کنید.
- **کاتالوگ خالیه یا نمی‌تونید وارد بشید:** پیش‌نیازهای داده و حساب رو توی بخش
  بالا چک کنید. حساب تازهٔ مدیر Strapi با حساب کاربر فروشگاه فرق داره.
- **پورت اشغاله:** فروشگاه‌ها پورت‌های پیش‌فرض 1337 و 2888 رو مشترک دارن.
  هر بار فقط یک محیط رو اجرا کنید، یا پورت و همهٔ آدرس‌های مرتبط رو با هم
  تغییر بدید. قبل از بستن هر پردازش، مطمئن بشید متعلق به کدوم پروژه‌ست.
- **ماژول کامپایل‌شدهٔ @repo/auth-core پیدا نمی‌شه:** بعد از نصب یا تغییر این
  پکیج، بیلدش رو طبق دستور بالا دوباره بزنید و برنامه رو ری‌استارت کنید.
- **اجازهٔ ساخت shim ندارید:** مستقیم `corepack pnpm` رو بزنید. اگر نصب به خطا
  خورد، قبل از دست زدن به لاک‌فایل نسخهٔ Node و pnpm رو چک کنید.

برای کار با برنچ و مرج ریکوئست، [راهنمای GitLab](gitlab-workflow.fa.md) رو ببینید.
